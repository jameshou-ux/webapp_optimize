# imToken Web App Revamp Workshop Plan

**Workshop / 工作坊:** Homepage and Web App Revamp Prioritization  
**Duration / 时长:** 60 minutes  
**Audience / 参与者:** PM, designers, engineering leads, business/GTM stakeholders, key decision makers  
**Core goal / 核心目标:** Gather structured stakeholder input for revamping `web.token.im`, then use simple voting to select prioritized options for prototyping or PRD detailing.

---

## 1. Workshop Intent / 工作坊意图

The workshop is not a blank brainstorm. It starts from known product context and current pain points, then turns stakeholder input into a prioritized decision set.

本次工作坊不是开放式头脑风暴，而是基于已有产品背景和当前问题，把各方输入整理为可推进的方案和优先级。

### Product framing / 产品定位

imToken Web App is a lightweight web portal to tokens and blockchain access. It is not a conventional wallet or static marketing site.

imToken Web App 是 Token 的轻量网页门户，是面向 Token 与区块链访问的探索型界面，而不是传统钱包或静态官网。

**Strategic line / 战略表达:**

> Browser + internet connection = token access from anywhere.

> 浏览器 + 网络连接 = 从任何地方访问 Token 世界。

### Foundation and stretched features / 产品结构

| Layer | Meaning | 中文说明 |
|---|---|---|
| Token foundation | Token pages should become the foundational destination where users understand and act on tokens. | Token 页面是用户理解、探索和执行行动的基础落点。 |
| Token actions | Send by Link, receive, claim, follow, and other token-level actions. | 围绕 Token 的发送、领取、关注、Claim 等行动。 |
| Token exploration | Collections as curated paths to understand token value, purpose, and insight. | 通过 Collection 策展方式帮助用户理解 Token 的价值、用途和洞察。 |

### Current problem summary / 当前问题摘要

| Area | Pain Point | 中文说明 |
|---|---|---|
| Positioning | The current homepage does not clearly explain what imToken Web is, what users can do, or why it matters. | 首页没有在首屏讲清楚产品是什么、能做什么、为什么值得用。 |
| Onboarding | New users lack a clear path from landing to account creation to first useful action. | 新用户从进入首页到账户创建再到第一次有价值行动的路径不清晰。 |
| Explore IA | Spatial/list views and collections are visually present but not yet clear enough as a guided token journey. | 空间视图、列表视图和 Collection 存在，但还没有形成清晰的 Token 探索旅程。 |
| Action discovery | Token actions are not exposed early enough or connected strongly enough to token understanding. | Token 行动没有足够早地暴露，也没有和 Token 理解过程强绑定。 |

## 2. Desired Outputs / 预期产出

By the end of the hour, the team should have:

工作坊结束时，需要形成以下产出：

1. **Categorized stakeholder inputs / 分类后的利益相关方输入**
   - New user journey from entry/onboarding to homepage and first token action.

   - 2-3 options for immediate prototype/detailing.
   - 2-3 follow-up bets.
   - Explicit rejected or parked ideas.

4. **Next-step ownership / 后续负责人**
   - Prototype owner.
   - PRD/detailing owner.
   - Data or research follow-up owner.
   - Decision owner.

## 5. Facilitation Script / 主持人脚本

### 0-5 min: Opening / 开场

**Say / 可以这样说:**

```text
Today we are aligning on how to revamp web.token.im around the Perfect Token Journey.

The homepage should not only look better. It needs to help new and existing users understand token value, enter with low friction through AA/passkey, and continue toward token pages where actions are available.

The output of this hour is a prioritized option set selected through simple voting, ready for prototype or PRD detailing.

今天我们要围绕 Perfect Token Journey 对齐 web.token.im 的改版方案。

首页不只是要变好看，而是要帮助新用户和老用户理解 Token 价值，通过 AA/passkey 低门槛进入，并继续走到具备行动能力的 Token 页面。

这一小时的产出是通过简单投票选出的优先级方案，可以进入原型或 PRD 细化。
```

**Decision frame / 决策框架:**

| We will decide | We will not decide |
|---|---|
| Which candidate options deserve prototype/detailing next. | Final visual design. |
| Which homepage job is highest priority. | Final copy. |
| Which journey needs to be tested first. | Full information architecture. |
| Which risks must be resolved before build. | Engineering timeline. |

### 5-12 min: Pain-point recap / 问题回顾

Use this short recap. Do not spend more than 7 minutes.

用以下方式快速回顾，不超过 7 分钟。

| Lens | Current Issue | Why It Matters |
|---|---|---|
| Product | Value proposition is abstract and hidden behind modal/help content. | Anonymous visitors cannot understand why to start. |
| User | No strong first journey from landing to account creation to token action. | Passkey and AA reduce friction, but the product does not fully turn that into activation. |
| Design | Spatial bubbles dominate attention but do not explain token meaning or action. | Visual interest does not yet convert into understanding or usage. |
| Growth | Campaign/referral traffic lacks a dedicated landing path. | New traffic is not converted into account creation or first action. |
| Trust | Beta and chain limitations lack roadmap framing. | Users may read constraints as unfinished product quality. |

**Prompt / 提问:**

```text
Given these pain points, what must the next homepage experience solve first?

基于这些问题，下一版首页最先必须解决什么？
```

### 12-25 min: Structured input capture / 结构化收集输入

Run silent writing for 5 minutes, then clustering for 8 minutes.

先 5 分钟静默书写，再 8 分钟聚类。

#### Input structure / 输入结构

Organize every input by **user type + journey stage**. This keeps the discussion focused on complete flows instead of isolated homepage components.

每条输入都按 **用户类型 + 旅程阶段** 组织。这样讨论会聚焦完整路径，而不是孤立的首页模块。

| User Type | Definition | 中文说明 |
|---|---|---|
| New user | Someone who has not used imToken Web before, may not have an account, and needs motivation plus confidence to start. | 第一次使用 imToken Web 的用户，可能没有账户，需要动机和信任感才会开始。 |
| Existing user | Someone who already has an account, holding, claim history, followed collection, or prior imToken brand trust. | 已有账户、持仓、领取记录、关注 Collection，或已信任 imToken 品牌的用户。 |

#### New user journey lane / 新用户旅程线

| Stage | Input Prompt | 中文提示 |
|---|---|---|
| Entry trigger | Where does this user come from before seeing the homepage? Campaign, friend link, search, social post, direct visit? | 用户看到首页前从哪里来？活动、朋友链接、搜索、社媒，还是直接访问？ |
| Onboarding need | What fear, confusion, or missing motivation must be solved before they create or use an account? | 创建或使用账户前，必须解决哪些恐惧、困惑或动机不足？ |
| Homepage landing | What should they understand within 5 seconds after landing on the homepage? | 落到首页后 5 秒内必须理解什么？ |
| Homepage job | Should the homepage persuade, teach, let them explore first, or push account creation? | 首页此刻应该说服、教育、允许先探索，还是推动创建账户？ |
| Next destination | Where should the homepage take them next: passkey signup, claim flow, collection, token page, or demo? | 首页下一步应把他们带去哪里：passkey 注册、领取流程、Collection、Token 页面，还是 Demo？ |
| First success | What is the first successful action that proves the product value? | 哪个第一次成功行动能证明产品价值？ |

#### Existing user journey lane / 老用户旅程线

| Stage | Input Prompt | 中文提示 |
|---|---|---|
| Return trigger | Why does this user come back: check holdings, claim, send by link, follow token news, browse collections? | 用户为什么回来：查看持仓、领取、Send by Link、关注 Token 动态，还是浏览 Collection？ |
| Re-entry state | What should the homepage know or reflect when they arrive signed-in or recognized? | 已登录或被识别后，首页应知道或呈现什么？ |
| Homepage landing | What should they get immediately without re-learning the product? | 他们不需要重新学习产品时，首页应立刻给什么价值？ |
| Homepage job | Should the homepage summarize holdings, surface pending actions, recommend collections, or route to token pages? | 首页应总结持仓、露出待处理行动、推荐 Collection，还是引导到 Token 页面？ |
| Next destination | Where should the homepage take them next: My Holdings, followed collection, token detail, send/receive, or claim activity? | 首页下一步应把他们带去哪里：My Holdings、已关注 Collection、Token 详情、发送/接收，还是 Claim 活动？ |
| Continued success | What repeat action or insight makes them come back again? | 哪个重复行动或洞察会让他们再次回来？ |
 
#### Cross-journey checks / 跨旅程检查

Use these checks after both lanes are filled:

两个旅程线填完后，用这些问题检查：

| Check | Prompt | 中文提示 |
|---|---|---|
| Shared homepage job | What must be true for both new and existing users? | 对新用户和老用户都必须成立的首页职责是什么？ |
| State split | What must change between anonymous, just-created, and returning states? | 匿名、刚创建账户、回访状态之间必须有什么差异？ |
| Token destination | How does each journey reach the foundational token page? | 每条旅程如何到达基础 Token 页面？ |
| Action exposure | Which token actions appear before account creation, after onboarding, and after return? | 账户创建前、onboarding 后、回访后分别露出哪些 Token 行动？ |
| Trust and insight | What trust signal, education, or token insight is needed before the next click? | 下一次点击前需要什么信任信号、教育内容或 Token 洞察？ |

#### Capture format / 记录格式

Every note should use this structure:

每条输入建议使用以下格式：

```text
As a [new/existing user] at [journey stage], I need [need/problem], so that [outcome].

作为处在 [旅程阶段] 的 [新用户/老用户]，我需要 [需求/问题]，从而 [结果]。
```

Examples:

示例：

```text
As a new user at homepage landing, I need to understand what I can do before creating an account, so that passkey signup feels worth it.

作为落到首页的新用户，我需要先理解不创建账户也能探索什么，从而让 passkey 注册变得有动机。
```

```text
As an existing user at homepage landing, I need Collections to explain why a group of tokens matters, so that I can move from browsing to token-level actions.

作为落到首页的老用户，我需要 Collection 解释一组 Token 为什么重要，从而从浏览进入 Token 级行动。
```

### 25-40 min: Option synthesis / 方案整理

Convert the clustered inputs into candidate options that can be voted on. This section should be fast and structured. Do not run a deep debate here.

把已经聚类的输入整理成可投票的候选方案。这里要快速、结构化，不做深入辩论。

#### Synthesis rules / 整理规则

1. Merge duplicate or highly similar ideas.
2. Split broad ideas into concrete options when they imply different work.
3. Keep each option tied to a user need, not only a UI component.
4. Name each option in one short sentence.
5. Capture the biggest open question only if it changes the next-step plan.

```text

User need:

Expected outcome:

First successful user action:

Must include:

Can defer:

Open question:

Prototype/PRD owner:
```

## 6. Simple Voting Method / 简单投票方法

Use simple voting as the main prioritization technique. The goal is to quickly identify where the room has the strongest conviction, not to calculate a perfect ranking.

本环节以简单投票作为主要优先级方法。目标不是计算完美排序，而是快速看出团队最有共识的方案。

### Voting setup / 投票设置

| Rule | Detail | 中文说明 |
|---|---|---|
| Voting budget | Each participant gets 3 votes. | 每位参与者有 3 票。 |
| Vote limit | A participant can put at most 2 votes on the same option. | 同一方案最多投 2 票。 |
| Voting basis | Vote for options that should move into prototype or PRD detailing first. | 投给最应该进入原型或 PRD 细化的方案。 |
| Tie-break | Decision owner breaks ties after hearing one short argument per tied option. | 平票时由决策负责人听取每个方案一句理由后决定。 |
| Output | Top 2-3 options become the prioritized shortlist. | 得票最高的 2-3 个方案成为优先级清单。 |

### Fast voting criteria / 快速投票判断

Before voting, ask participants to consider four simple questions:

投票前请大家用四个简单问题判断：

1. Does this directly improve the Perfect Token Journey?
2. Does this help users reach token pages or token actions?
3. Is this important for both new understanding and product usage?
4. Can this realistically move into prototype or detailing next?

### Post-vote grouping / 投票后分组

| Group | Definition |
|---|---|
| Move forward / 立即推进 | Top 2-3 voted options with clear owner and next artifact. |
| Keep warm / 保留观察 | Valuable options that did not win but may support the selected work. |
| Park / 暂停 | Ideas outside the current homepage and token journey scope. |

## 9. Facilitator Fallback / 主持人兜底方式

If the voting result is scattered, do not introduce a new option in the room. Instead, group the highest-voted items into practical next-step tracks.

如果投票结果分散，不要现场引入新方案。主持人应把高票项整理成可推进的下一步轨道。

| Track | Use When | Output |
|---|---|---|
| Homepage promise track | Top ideas cluster around positioning, value proposition, and CTA. | Homepage message and landing flow prototype brief. |
| Token journey track | Top ideas cluster around token page, actions, and first successful action. | Token journey PRD or flow prototype brief. |
| Exploration track | Top ideas cluster around Collections, spatial/list view, and insights. | Explore IA prototype brief. |

主持人可以这样收口：

```text
The votes do not show one single winning concept, but they do show the strongest problem area.
We will package the top-voted ideas into one prototype/PRD track, assign an owner, and keep the remaining ideas as supporting inputs.

投票没有产生单一压倒性方案，但已经显示了最强的问题区域。
我们会把高票想法整理成一个原型/PRD 轨道，指定负责人，其余想法作为支持输入保留。
```
